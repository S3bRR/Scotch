# Scotch app and runtime update plan

Implemented locally, November 14, 2026, with the user’s subsequent instruction to expose **one Update action** for app and runtime updates together. The two services remain separate internally. See [updates.md](updates.md) for implementation, verification, and activation instructions. Public feed deployment, pushes, tags, releases, and scheduled workflow activation remain pending the user's testing/release instructions.

The initial design discussion below is retained as rationale. Its separate app/runtime UI actions are superseded by the combined Update command, which reports and applies both parts in a single flow. Old runtime sets and prefix snapshots are retained; automatic pruning is deferred to avoid deleting a referenced recovery copy.

## What the screenshots show

The yellow `D3DMetal: - → d3dmetal-3.0` banner is generated by `RuntimeInstallerService.overlayDrifts()`. It compares the local manifest with versions compiled into Scotch. An absent optional D3DMetal has a nil version, which is treated as a mismatch and presented as an update.

`RootView.driftBanner` opens the setup sheet when Update is pressed. `AppViewModel.installRuntimeDependencies()` then downloads and reinstalls the whole pinned runtime. It does not update the Scotch application. When the D3DMetal archive returns 404, setup now continues successfully without it, but recomputing overlay drift recreates the same banner. This was left incomplete by the optional-D3DMetal fix. The local installer probe even expects a missing optional overlay to remain a drift; that assertion must change.

The D3DMetal download URL was checked again during this investigation and returned HTTP 404. A tag or a version string does not establish that an installable release asset exists.

`fetchLatestReleases()` is also misleadingly named: it fetches specified release tags, not the latest versions. `shouldUpdateRuntime()` compares installed components against the compiled-in matrix. Neither currently consumes a remotely maintained update feed. The runtime-update setting therefore cannot deliver a new runtime matrix without a new Scotch build.

## Product decisions

Use separate app and runtime update services, with separate installed versions and progress. Keep optional backend availability separate from both.

| Operation | Proposed behavior |
| --- | --- |
| Check for Scotch updates | Check the published stable app feed on launch if due and about daily while Scotch is open. Always allow a manual check. |
| Check for approved runtimes | Fetch a small signed runtime manifest on the same daily cadence; download files only when an eligible approved update is selected or automatic installation is enabled. |
| Discover newer upstream components | A weekly repository workflow discovers candidate stable releases and prepares a tested candidate change. It does not immediately deploy arbitrary upstream releases to users. |
| Install updates | Stage downloads in advance; activate only after games, bottle setup, and other runtime operations have finished. Start with prompted installation; offer automatic installation while idle after the update path is validated. |
| Scotch is closed | Check when next launched. A continuously running background agent is unnecessary for the initial implementation. |

Manual checks bypass the time limit. Store successful-check times, cache validators, and notification versions. Use bounded retries and preserve a working installation when a check fails. Being offline is not a reason to reopen setup. A failed check must not be represented as proof that everything is current.

## Phase 1: correct update status and maintenance actions

1. Model distinct component states: installed/current, newer approved version available, missing optional component, required repair, download unavailable, and incompatible with this Scotch/macOS version. Treat checking and check failures separately.
2. Show an Update action only for a compatible target with a published, verified package. Missing optional D3DMetal should appear as an availability note in Settings, not a global update warning. If a user explicitly needs that backend, explain the missing package. When a real package becomes available, offer a targeted Install D3DMetal action.
3. Treat an older supported version versus a newer experimental local version as a compatibility choice, not automatically an upgrade. A version inequality alone is insufficient.
4. Stop routing all update actions to initial setup. Distinguish first-run setup, runtime maintenance, component installation, and Scotch application updates. An unavailable optional download must not trigger another full Wine download.
5. Recompute state after installation and on restart. An unavailable target should not repeatedly prompt until availability/feed revision changes or the user explicitly retries.
6. In maintenance UI, retain an existing usable runtime on failure and allow the user to return to Scotch. Do not label every maintenance exit Quit.
7. Add regression coverage at the status/view-model boundary. Change the existing missing-D3DMetal drift assertion to ensure it produces no actionable update. Test pressing the maintenance action through completion, not just installer success.

This phase should be fixed and tested before treating the current 1.2.4 test DMG as release-ready. Replacing the banner with an unconditional dismissal would hide actual updates and repairs; correct the state calculation instead.

## Phase 2: update the Scotch application through GitHub

Use Sparkle 2 for app replacement, signature verification, update prompts, and relaunch. Add it only to the app target, keeping the CLI and thumbnail extension independent of the updater dependency.

Proposed hosting, not yet configured:

- Keep app downloads in S3bRR/Scotch GitHub Releases, under immutable versioned URLs.
- Serve the stable appcast at an HTTPS GitHub Pages URL, for example `https://s3brr.github.io/Scotch/updates/appcast.xml`.
- Use incrementing CFBundleVersion values to select app builds and CFBundleShortVersionString for display. Preserve the existing bundle identifier `com.s3brr.Scotch` and app name.
- Embed the feed address and public EdDSA update key in the app. Keep the private key outside source control, with a backup and a deliberate recovery/key-rotation policy. Do not ship a GitHub write token in Scotch.
- Sign the final update archive and verify it before installation. A SHA256 file and an ad-hoc code signature do not replace an authenticated update signature. Developer ID signing and notarization are recommended separately; the updater path must be tested with the signing method actually used for the release.
- Continue distributing Scotch.dmg for manual installation. Sparkle supports DMG updates, so a separate update ZIP is optional. If a ZIP is chosen, preserve bundle symlinks and signatures.
- Update package_release.sh to embed and sign Sparkle.framework and its required nested helpers, preserve permissions/symlinks, and set the appropriate framework search path. The current script only stages the existing app products and resource bundles.
- Add Check for Scotch Updates in the app menu and show app-update preferences/status separately from runtime maintenance.

Before any updater-triggered quit, check for running Wine/game processes, bottle creation, winetricks, and runtime installation. The current application termination path invokes performTerminationCleanup and defaults to killing bottle processes. The updater must defer rather than unintentionally activating this behavior during a game. Coordinate pending app and runtime updates so they cannot race one another.

An app running from a mounted DMG or an unwritable location needs a clear installation/action message. Test these cases rather than assuming the app can replace itself in every location.

Existing 1.2.3 and the current 1.2.4 test build do not contain an app updater. Those users need one manual installation of a build that includes it. After that, later supported app releases can arrive in-app. The present Update button cannot bootstrap this capability remotely.

## Phase 3: deliver approved runtimes without an app release

Introduce a signed, versioned runtime feed independent of the appcast. This replaces the compiled-in matrix as the authoritative source of approved downloadable updates, while retaining a bundled supported baseline for bootstrap/fallback as appropriate.

The manifest should identify a tested runtime set and each component's exact version, immutable asset URL, byte size, SHA256, architecture, supported macOS range, minimum Scotch version, package layout revision, dependency/capability requirements, and availability. Include a monotonically increasing feed revision and signature. Use a separate runtime signing key so its lifecycle is independent of the Sparkle key.

Do not let the feed supply shell commands, executable install scripts, arbitrary destination paths, or unsupported layouts. Clients verify signatures, applicable revisions, hashes, expected architecture and archive contents, including rejection of path/symlink escapes. A new packaging layout or protocol that the client cannot understand requires a Scotch update first.

Maintain approved combinations of Wine, MoltenVK, DXVK-macOS, DXMT, and Mesa/Zink. Updating whichever upstream project has the largest version independently can break the combination. Select exact artifacts for the macOS/Wine backend rather than substituting a different upstream build with a similar name. D3DMetal needs an actually available distribution artifact before it can be advertised; automation cannot create a missing archive merely by checking more often.

Use versioned runtime sets with one shared runtime-location resolver instead of replacing the global Libraries tree under running processes. Existing bottles should initially retain the working set they were using. New bottles can use the latest approved set; existing bottles can upgrade through a controlled, recoverable operation. Add the runtime-set reference to bottle metadata with a backward-compatible migration.

Download only missing/changed component packages into a cache, extract into a staging area, verify the entire candidate set and Wine.app signature, and commit the selected set only after success. Keep the previous set for rollback. Persist transaction state so a force quit or power loss during activation can be recovered on the next launch. Garbage-collect old sets only when no bottle references them and a useful rollback set remains.

An interim implementation can keep the existing Libraries layout while introducing a signed feed and safe transactions. Per-bottle runtime selection and protection from prefix upgrades must be implemented before silently moving all existing bottles to newer Wine versions.

## Preserve bottles, saves, and settings

Scotch already separates its app bundle from user data. AppPaths stores default bottles under `~/Library/Application Support/com.s3brr.Scotch/Bottles/`, with settings and catalogs in the parent directory. Libraries is a sibling runtime directory. BottleCatalog records custom/external bottle locations.

App updates must replace Scotch.app in place while preserving those directories, stable bundle identifiers, bottle IDs, catalog paths, metadata, registry files, pinned programs, per-program settings, and saves. Preserve the CLI link when the installed app path is unchanged, and verify/repair it if necessary. Updating must never invoke Uninstall; that service deliberately removes user data.

Before changing settings/catalog/metadata schemas, write backups and use versioned, idempotent migrations with atomic writes and validation. If a future schema is unsupported, stop with a recoverable message rather than rewriting it with missing fields. Keep external/unmounted bottle references; an unavailable drive is not evidence that a bottle should be removed. In particular, review BottleRepository.loadCatalog's fallback behavior: a failed decode must not silently replace an existing custom-location catalog with an empty/default discovery result during an upgrade.

Wine can modify a bottle prefix when run with a newer Wine version. Retaining the older runtime alone does not undo these prefix changes. Before a migration that changes a prefix, stop its processes and create a recoverable snapshot/backup of the affected prefix, with a disk-space check. Explain and test restoration. Routine app-only updates should not copy entire game libraries or run wineboot. Back up metadata cheaply; reserve full prefix copies/snapshots for operations that need them.

For the current manual test, quit Scotch and replace Scotch.app in Applications with the app from the new DMG. Leave Application Support and custom bottle folders in place. Do not use Uninstall as an update step.

## Phase 4: weekly discovery and reliable publication

Add a weekly GitHub Actions candidate-discovery workflow, with manual dispatch as well. Check relevant upstream stable releases, expected artifacts, checksums, supported architectures, and known package layouts. Produce a candidate pull request/report with exact version changes. Require package extraction and installer recovery tests plus appropriate macOS/Wine smoke tests. GPU/game checks that hosted CI cannot exercise reliably remain a separate validation step.

After validation and maintainer promotion, sign and publish the new runtime manifest. Clients receive the new approved runtime without requiring a new Scotch binary when the existing client supports its schema and layouts. A failed candidate leaves the published stable manifest unchanged.

For app releases, build from the reviewed release source, verify packaging, sign the final update archive, upload immutable release assets, verify their actual public downloadability/content, and only then publish the appcast item. Use separate metadata for app releases and runtime sets so a runtime-only publication does not accidentally become GitHub's latest Scotch app release. Never announce a version in a feed before its assets are usable.

Keep stable and test channels distinct. Permit withdrawing a bad release from future offers and retain prior artifacts for recovery. Automatic rollback of arbitrary app/data migrations is not assumed to be supplied by Sparkle; define and test that separately.

## Acceptance checks

- Optional D3DMetal absent or 404: setup finishes; no persistent Update banner; restart stays usable; no full-runtime redownload from an optional-component action.
- Genuine approved runtime update: visible distinct action; correct target is installed; status clears after success/restart.
- Required runtime damaged: repair is offered separately from an app update.
- Offline, stale/invalid feed, missing asset, corrupt archive, bad signature/hash, unsupported OS/architecture/schema, insufficient disk, and interrupted installation: existing working app/runtime and user data remain usable or recoverable; no false success.
- Game, Wine server, winetricks, bottle creation, or another update active: activation/restart defers and does not kill the operation.
- Older Scotch to updater-enabled Scotch through manual app replacement: same bottles, saves, settings, external paths, pins, registry data, and CLI integration remain present.
- Two updater-enabled app builds: real signed update download, app replacement/relaunch, version detection, no repeated prompt for an installed/skipped version, and no data loss. Test the final packaged artifacts, not only developer binaries.
- Mounted-DMG and unwritable-app cases: an understandable action instead of a silent failure.
- Runtime/prefix migration failure and rollback: original prefix contents and metadata can actually be restored; test with save-file fixtures and external/unmounted bottles.
- Release gate: every advertised asset is downloadable and verified; optional unavailability does not become an update loop.

## Implementation map and order

1. Fix component state and the banner first: RuntimeModels, RuntimeInstallerService, AppViewModel, RootView, SetupSheetView, and RuntimeInstallerProbe. Rebuild the local test DMG.
2. Establish migration/backups and preservation tests, then add app updating: Package.swift, ScotchApp, an app update coordinator, app Info.plist, packaging/verification scripts, and appcast generation.
3. Add signed runtime feed parsing/planning and transactions, then runtime-location resolution and per-bottle set selection. Update EnvironmentAssembler, WineRuntimeService, the generated Wine launcher, BottleSettings, and CLI paths together so all entry points use the same selected set.
4. Add weekly candidate discovery and publication tooling after client validation. Publish only after user testing and explicit release instructions. The existing instruction not to push remains in effect.

## Build 12 implementation status

The current implementation supersedes the original separate-action proposals:
one Update action checks the app and runtime services, names the components,
repairs legacy graphics if needed, installs approved compatible sets, and resumes
checks after app replacement. Upstream discovery remains a weekly read-only
candidate report, never untested automatic promotion.

The original 404 is removed. Pinned GPTK 3.0-3 plus WineForge 0.6.0.3 supply the
actual D3DMetal payload/loader ABI; DXMT also uses that compatible builtin engine.
MoltenVK 1.4.2 fixes 32-bit DXVK; private x86_64 KosmicKrisp supplies Zink's missing
Vulkan features. Per-instance native routing permits additive Zink alongside
Direct3D. See d3dmetal-repair.md and scripts/graphics/README.md for the tested
matrix, build/source distribution and limits.

Legacy repair is a staged full-Libraries transaction independent of unpublished
feeds. Native profiles are client-coupled; approved future combinations require
matching layouts/minimum builds and backward support for pinned older sets.
D3DMetal layout 3 and DXMT layout 2 require minimumAppBuild 12. Engine changes
snapshot full prefixes, including first launch of an older Metal-selected bottle.
App replacement retains data and metadata backups. User game testing, public
feeds, pushes, tags and releases remain pending explicit release instructions.
